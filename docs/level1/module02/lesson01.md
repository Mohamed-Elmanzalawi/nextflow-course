# Lesson 2.1: The Bash that Nextflow relies on

!!! info "About this lesson"
    **You'll learn** the five Bash behaviours that decide whether a Nextflow task **succeeds, fails, or silently lies**:

    1. exit codes;
    2. `set -e`, `-u` and `pipefail`;
    3. symlinks;
    4. `$` variables and escaping;
    5. stdout vs stderr.

    **Why it matters:** you know Bash well, but Nextflow uses it in a particular way. Every process's `script:` block **is** a Bash script, and Nextflow judges it **only by its exit code**. This lesson is short and focused on exactly those details.

    **Time:** about 1 h · **Level:** Beginner · **Needs:** a terminal

    **Docs:** [Process scripts](https://docs.seqera.io/nextflow/process) · [Process `shell` setting](https://docs.seqera.io/nextflow/reference/process)

!!! flo "Flo says"
    You already speak Bash, so this one's a speed round. But stay sharp: one of today's bugs fooled `set -eu` itself!

## A. Concept

### 1. Exit codes: the only thing Nextflow trusts

When a task's script finishes, Nextflow looks at its **exit code**:

| Exit code | Meaning | What Nextflow does |
|---|---|---|
| `0` | Success | Collects the outputs and passes them downstream |
| `1`–`127` | Some error | Marks the task **failed** (later you'll choose: stop, retry, or ignore) |
| `137` = 128 + 9 | Killed with `SIGKILL`, often **out of memory** | Same; a classic reason to **retry with more memory** (Module 12) |
| `143` = 128 + 15 | Terminated with `SIGTERM`, often a **time limit** | Same; often fixed by asking for more time |

Nextflow **never reads your output to judge success**. If your script prints garbage but exits `0`, the garbage flows on to the next step.

### 2. Nextflow runs every task with `bash -ue`, but **not** `pipefail`

Each task script starts with this line (taken from a real task, Nextflow 26.10.7):

```bash title="work/…/.command.sh (generated by Nextflow)"
#!/bin/bash -ue
```

| Flag | Effect |
|---|---|
| `-e` | Stop at the first command that fails |
| `-u` | Using an undefined variable is an error |
| *(no `pipefail`)* | In `cmd1 | cmd2`, **only `cmd2`'s exit code counts**. A failing `cmd1` is ignored! |

!!! protip "Pro tip: turn on `pipefail` for every task"
    Add this line to your pipeline's `nextflow.config`, and every task runs with `pipefail`:

    ```groovy title="nextflow.config"
    process.shell = ['/bin/bash', '-euo', 'pipefail']
    ```

    Tested: with this setting, the same `false | true` task **fails** with exit status 1. nf-core pipelines set an equivalent option. You'll learn about config files in Module 7.

### 3. Symlinks: how your input files reach a task

Every task runs in its **own folder** under `work/`. Nextflow doesn't copy your input files there; it creates **symbolic links** (symlinks) pointing to the originals. A real task folder:

```text title="ls -l inside a task folder (real output)"
lrwxr-xr-x input.txt -> /…/nf21/input.txt
```

--8<-- "includes/anim/staging.html"

That's fast, even for 50 GB BAM files, but it has consequences:

- **Never modify an input in place.** You'd be editing the original file through the link.
- **Published results are symlinks by default.** `publishDir` without `mode: 'copy'` puts *links into `work/`* in your results folder. Delete `work/` and your "results" break. That's why the Lesson 1.1 preview used `mode: 'copy'`.

### 4. `$`: Nextflow variable or Bash variable?

A `script:` block is a **Nextflow string that becomes a Bash script**. Nextflow replaces `${...}` with its own values **before** Bash runs. To keep a `$` for Bash, escape it with a backslash: `\$`.

```groovy title="Inside a process (tested)"
script:
"""
greeting="hi from bash"
echo "\$greeting and ${f.name}"
"""
```

```text title="Real output"
hi from bash and input.txt
```

- `\$greeting` → Bash sees `$greeting`, a **Bash** variable.
- `${f.name}` → Nextflow inserts the file name **before** Bash runs.

And a mistake you'll see: an undefined Bash variable makes the task fail, thanks to `-u`. Real error:

```text title="Real output"
Command error:
  .command.sh: line 2: NOT_DEFINED_ANYWHERE: unbound variable
```

!!! gotcha "Gotcha! Quote your globs on the command line"
    ```bash title="Terminal"
    nextflow run main.nf --reads data/*.fastq      # ✗ your shell expands the * first
    nextflow run main.nf --reads 'data/*.fastq'    # ✓ Nextflow receives the pattern
    ```

    Without quotes, `--reads` receives only the **first** file and the rest become stray arguments. Try `echo data/*.fastq` vs `echo 'data/*.fastq'` in the Lesson 1.1 folder to see the difference.

### 5. stdout vs stderr

Nextflow saves each task's standard output to `.command.out` and its standard error to `.command.err`. Send **messages and errors to stderr** (`>&2`) and keep **stdout for data**, so diagnostics never end up mixed into results.

!!! analogy "Real-life analogy: a lab technician's report"
    The **exit code** is the technician's thumbs up or thumbs down. **stdout** is the result sheet. **stderr** is the note saying what went wrong. Nextflow's lab manager only looks at the thumb.

## B. Demonstration: a bug that fools `set -eu`

The lesson folder has:

- `make_data.sh`, which creates `good.fastq.gz` (1,000 reads) and `truncated.fastq.gz`, a download that stopped at 40 %;
- `count_reads.sh`, which counts reads in a gzipped FASTQ.

```bash title="Terminal"
cd ~/Desktop/Projects/learning_nextflow/module02_environment/lesson01_bash_refresher
bash make_data.sh
bash count_reads.sh data/good.fastq.gz;      echo "exit code: $?"
bash count_reads.sh data/truncated.fastq.gz; echo "exit code: $?"
```

??? predict "Predict: what does the corrupt file report?"
    Real output from this Mac:

    ```text title="Real output"
    Created data/good.fastq.gz (1000 reads) and data/truncated.fastq.gz (corrupt)
    1000
    exit code: 0
    gzip: data/truncated.fastq.gz: unexpected end of file
    gzip: data/truncated.fastq.gz: uncompress failed
    0
    exit code: 0
    ```

    `gzip` complains, but the script reports **0 reads** and **exits 0**. A Nextflow pipeline would accept that as success and carry on with an empty sample. (On Linux, GNU `gzip` may print a partial count instead, which is just as wrong.)

| Line | Code | The problem |
|---|---|---|
| 4 | `set -eu` | Looks safe, but without `pipefail`, `-e` only sees the **last** command of a pipe. |
| 6 | <code>gzip -dc "$1" &#124; awk …</code> | `gzip` fails (exit 1), `awk` happily prints `0` and exits 0, so the pipe "succeeds". |
| 6 | `"$1"` | Even a **missing argument** escapes `-u` here: the error happens inside the pipe, and `awk` still exits 0. |

## E. Independent challenge

Create `count_reads_safe.sh` in the lesson folder. It must:

1. print **just the number of reads** and exit `0` for a good file;
2. exit **non-zero** for a corrupt file, **without printing a misleading count**;
3. exit non-zero with an error message **on stderr** if the file doesn't exist;
4. exit non-zero if it's called with **no argument**.

```quiz

label: "Challenge: auto-checked"

hint: "Three tools: `set -o pipefail`; checking the arguments and the file yourself (`$#`, `[[ -r file ]]`, `>&2`, `exit 2`); and capturing the count in a variable (`count=$(…)`) so nothing is printed if the pipe fails."
explain: |
  - **`pipefail`** makes a `gzip` failure fail the whole pipe.
  - **`count=$(…)`** inside `set -e` means the script stops *before* `echo`, so no misleading number is printed.

```

## G. Summary

| Idea | Remember |
|---|---|
| Exit code | `0` = success; anything else = failure. Nextflow trusts **only** this. |
| `bash -ue` | Nextflow's default task shell: stop on errors and on unset variables |
| `pipefail` | **Not** on by default. Add `process.shell = ['/bin/bash', '-euo', 'pipefail']`. |
| 137 / 143 | Killed (often memory) / terminated (often time limit) |
| Symlinks | Inputs are staged as links. Never edit inputs; use `mode: 'copy'` for results. |
| `\$var` vs `${var}` | Bash variable vs Nextflow variable inside `script:` |
| stdout / stderr | Data / messages, saved as `.command.out` / `.command.err` |
